تعلن ملفات manifests للتطبيقات الـ35 ذات المصدر ترخيص LGPL-3. هذه قراءة للترخيص المعلن وليست تدقيقًا قانونيًا شاملًا لكل اعتماد أو أصل. استخدام Enterprise يتطلب المصدر والترخيص المناسبين؛ تغيير اسم البطاقة أو installable أو صلاحية المستخدم لا يوفر الوظيفة. يستطيع المطور بناء إضافات NASQO أصلية للمتطلبات المعتمدة، مع الحفاظ على تراخيص المكونات وإشعاراتها.

**التصحيح الأهم:** بطاقة «المحاسبة» رقم 702 هي `accountant` (غير مثبتة/بلا مصدر، وحالتها uninstallable). أما `account` و`account_payment` فمثبتان. `account_accountant` و`account_reports` غير موجودتين في المصدر ولا في سجل الوحدات المفحوص. اسم «الفوترة» المعروض لـ`account` لا يعني أن المحرك يفتقر إلى نماذج القيود والمدفوعات؛ كما أن وجود هذه النماذج لا يثبت توفر كل تقارير وواجهات Accounting Enterprise.

الصفحة المعروضة هي كتالوج تقني لإدارة إضافات قاعدة Odoo، وليست كتالوج استحقاقات التاجر في SaaS. تخصيص الهوية في `nasqo_apps_identity` عرضي فقط؛ لا يغير الترخيص أو الصلاحيات أو ما هو مثبت.

`account_payment` يربط المحاسبة بمزودي الدفع/دفع الفواتير عبر البوابة؛ ليس مرادفًا لوحدة سندات NASQO. نماذج المدفوعات والقيود الأساسية تُعاد استخدامها بدل نسخها.

لم توجد في مسارات المصدر المفحوصة وحدات `nasqo_finance` أو `nasqo_fx` أو `nasqo_partner_credit` أو `nasqo_reports` أو `nasqo_notifications`. غياب هذه الأسماء لا يعني غياب كل وظائفها المقصودة في Odoo القياسي.

لا يوجد اعتماد وحدة مفقود المصدر ضمن الإغلاق التكراري لتبعيات التطبيقات الـ35 المتاحة. من التطبيقات الـ11 غير المثبتة، يحتاج `website_event` أيضًا إلى تثبيت `event`؛ بقية تبعياتها القياسية في اللقطة مثبتة. هذا لا يشمل إثبات صلاحية جميع مكتبات Python أو الأدوات الخارجية أو الموارد اللازمة، ولا يضمن نجاح التثبيت.

## 5. تصميم كتالوج NASQO المقترح

هذا تصميم موثق فقط؛ لم يُنفذ تغيير في الواجهة.

يفصل عرض المطور بين أربعة أمور: وجود المصدر، وحالة التثبيت، والاستحقاق التجاري، ونتيجة الاختبار. تعرض البطاقة اسم الوحدة والإصدار والترخيص وموانع التثبيت والمرحلة ونتيجة التحقق. مرشحات مناسبة: «مثبت»، «متاح للاختبار»، «ضمن خطة NASQO»، «يتطلب مصدرًا وترخيصًا إضافيين». لا يُعرض التطبيق أنه مكتمل لمجرد وجود أيقونته.

التاجر يرى الوظائف المعتمدة في باقته، بينما تثبيت/ترقية/إزالة الإضافات وإعدادات النظام تبقى لمشغل المنصة المصرح له. لا يكفي إخفاء Apps أو زر التثبيت: RBAC-02 يختبر UI وRPC والروابط المباشرة وdebug=1، وRBAC-08 يختبر اتحاد المجموعات والأساليب العامة والدفعات. لا تُمنح صلاحيات الإدارة العامة لتجاوز بطاقة غير متاحة.

مستخدم الدعم يحتاج تفويضًا محدودًا بالمتجر والسجل والوقت مع audit، ورفضًا عند انتهاء التفويض أو فشل خدمة التفويض/التدقيق (RBAC-04/05/06/11). لا يعالج تثبيت helpdesk هذه الضوابط وحده. فصل قواعد البيانات وFilestore هو عزل المستأجرين؛ Multi-website أو مجموعة شركة في قاعدة واحدة ليست بديله.

أوامر التحقق المحلية: `python3 -B -m unittest discover -s tests -v` و`git diff --check`، مع فحص Python مباشر لسلامة JSON/CSV والروابط وAST والأنماط المذكورة. لم تُضف اختبارات معاملات بديلة إلى هذه الجولة. حالة Actions على فرع المراجعة يجب قراءتها من GitHub؛ نجاح اختبارات التأسيس لا يغيّر حالات BLOCKED المالية أعلاه.

## 8. إعادة الفحص والتسليم

تشغّل السكربتات في جلسة Odoo shell موثوقة خاصة بالبيئة المقصودة. مثال من داخل حاوية مُهيأة، مع تكييف المسارات وقاعدة الاختبار:

```bash
odoo shell -c /etc/odoo/odoo.conf -d "$AUDIT_DB" --no-http < scripts/audit/module_catalogue.py
odoo shell -c /etc/odoo/odoo.conf -d "$AUDIT_DB" --no-http < scripts/audit/runtime_capabilities.py
```

لا تمرر كلمة مرور في سطر الأوامر أو تحفظ السجل الخام في Git. يُحتفظ فقط بـJSON الذي يبدأ بـNASQO_CATALOGUE_JSON أو NASQO_CAPABILITIES_JSON بعد مراجعته. النتيجتان من هذه الجولة حُفظتا بعد استخراج العلامة؛ نهاية كل سكربت rollback ولا توجد فيه استدعاءات ORM للكتابة.

فرع المراجعة: `docs/nasqo-app-catalogue-review` فوق شجرة فرع الهوية. قاعدة النشر في GitHub: `3e6c3b87c270c1ebb7a836421f6376d7ffb3f2fb`؛ الشجرة المطابقة محليًا `1e9a2f346e6fb6639ba69dbe374b9a8828b40828`. لا دمج لـPR #1 أو #6، ولا نشر تطبيقات على الخادم ضمن هذه الجولة.
