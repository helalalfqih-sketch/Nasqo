# خطة التنفيذ التقنية لمنصة NASQO باستخدام Odoo Community 19

**مرجع التحليل:** «الخطة التفصيلية لتحليل وإعادة بناء تطبيق المحاسب الذكي برو» – النسخة الموسعة ذات 11 صفحة (`downloadfile-1.docx`)، إعداد 11 نوفمبر 2026.
**حالة الوثيقة:** Technical Implementation Plan v1.0 – تصميم للتنفيذ والمراجعة، **غير منفذ في الشيفرة**.
**تاريخ الخطة:** 13 نوفمبر 2026. **النطاق:** NASQO SaaS + وحدات ERP/Accounting اختيارية لمتاجر العملاء.
**قاعدة تشغيلية:** يمنع تعديل NASQO ERP الإنتاجي أو متجر Shopify الحالي أو دمج PR #1 أو استيراد بيانات حقيقية في الاختبارات استنادًا إلى هذه الوثيقة وحدها.

## 1. الملخص والقرارات الهندسية

تهدف NASQO إلى تمكين التاجر من إنشاء متجر مستقل وإدارته عبر Odoo Community 19، مع إتاحة وظائف محاسبية ومخزنية مأخوذة كمتطلبات **مرجعية** من صور «المحاسب الذكي برو». ننفذ **القدرات والسيناريوهات** ولا ننسخ تصميم التطبيق الأصلي أو شيفرته أو أصوله.

**القرارات المقترحة:**

1. **Odoo هو النظام المرجعي لمعاملات المتجر:** منتجات `product.template`، أوامر `sale.order`، الموردون `res.partner`، المشتريات `purchase.order`، المخزون `stock.*`، الفواتير والقيود `account.move` و`account.move.line`. لا نبني قاعدة جداول محاسبية موازية لمجرد ورودها في الوثيقة الأصلية.
2. **عزل كل تاجر:** قاعدة PostgreSQL مستقلة + Filestore مستقل + هوية نطاق ونسخ احتياطية تخصه. التشغيل بحاويات مشتركة أو معزولة يُقرّر بحسب الأداء ومستوى المخاطر؛ العزل في التطبيق وحده ليس كافيًا.
3. **Control Plane مستقل:** تسجيل مستخدمي المنصة، باقات الاشتراك، إنشاء المتاجر (Provisioning)، التوجيه للنطاقات، الفوترة والحدود والمراقبة. بيانات المبيعات والمخزون والقيود تبقى في قاعدة المتجر.
4. **فصل مرحلتين من المنتج:** إطلاق متجر SaaS أساسي أولًا؛ ثم إطلاق حزمة «إدارة مالية متقدمة» بعد اعتماد النموذج المحاسبي وإكمال اختباراته. لا تتوقف الوظائف الأساسية للمتجر على اكتمال صرف العملات أو الرسائل.
5. **المحاسبة ليست تجميع أرصدة نصية:** حركات مرحّلة مزدوجة ومتوازنة، عملات وسعر صرف مؤرخ، معرّف عملية مانع للتكرار، سجل تدقيق؛ التسويات بقيود عكسية بدل حذف التاريخ.
6. **Cloud وMobile:** النسخة الأولى Web Responsive باللغة العربية RTL. تطبيق Flutter/SQLite/Drift المقترح في وثيقة المرجع خيار مستقل لمرحلة لاحقة؛ لا يصبح SQLite مصدرًا للحقيقة المحاسبية بدل PostgreSQL/Odoo.

**حدود Odoo Community:** الوحدة `account` في مصدر Odoo Community 19 تحمل اسم **Invoicing**، وليست وعدًا بكل قدرات Accounting Enterprise. قبل اعتماد دفتر أستاذ متقدم أو مطابقة بنكية أو تقارير مالية كاملة تُنفذ Gap Analysis واختبارات على الإصدار المثبّت، ثم يُحدَّد تطوير مخصص/إضافة مفتوحة المصدر مرخّصة ومراجعة. لا يُفترض وجود `l10n_ye` في المصدر المرجعي دون تحقق؛ تُراجع متطلبات التوطين والضرائب محليًا قبل التفعيل.

## 3. المعمارية المرجعية وملكية البيانات

```text
المستخدم / التاجر
   |  HTTPS + DNS + Rate Limit + WAF
   v
بوابة NASQO SaaS (Control Plane)
   |-- التسجيل والتحقق / MFA / RBAC
   |-- سجل المتاجر، الباقات، الفوترة، Audit Log
   |-- API + Queue + Provisioning Worker (idempotent)
   |-- Domain Router / Certificate Controller
   |-- Monitoring / Backup Orchestrator
   |
   +---- Tenant A: Odoo 19 + db_A (PostgreSQL) + filestore_A
   +---- Tenant B: Odoo 19 + db_B (PostgreSQL) + filestore_B
                     |
             Website + Sales + Purchase + Inventory
             Invoicing + NASQO Custom Add-ons
```

**حدّ البيانات:** Control Plane يحتفظ بـ`tenant_id`، حالة المتجر، الاشتراك، النطاق، مالك المتجر، حدود الباقة، وأحداث التهيئة. لا يحتفظ بنسخة مستقلة من قيود `account.move.line` أو المخزون. واجهة التاجر تستخدم واجهات مصرحًا لها في قاعدة متجره؛ الدعم لا يحصل على صلاحية إدارة البيانات افتراضيًا.

**Lifecycle لإنشاء متجر:** `requested → validating → provisioning → initializing → verifying → active`، أو `failed_needs_review`. يستخدم `Idempotency-Key` و`tenant_id` فريدًا وإعادة محاولة مضبوطة، مع حذف موارد الفشل فقط بعد التأكد من عدم وجود بيانات مستخدم. النطاق يُربط بالمستأجر بعد التحقق من الملكية ومطابقة قاعدة البيانات. عند التوسع، تُستخدم حاويات/خدمات Odoo منفصلة لكل مجموعة أو تاجر كبير؛ لا يُفرض Container مستقل لكل متجر منذ اليوم الأول دون قياس التكلفة.

**مثال عقد API مقترح، غير موجود حاليًا:** `POST /api/v1/stores` لطلب الإنشاء و`GET /api/v1/store-operations/{operation_id}` لحالة المهمة. طلب الإنشاء يستقبل اسم المتجر وslug والخطة والعملة واللغة، **ولا** يستقبل اسم قاعدة البيانات أو صلاحيات إدارية يحددها العميل.

**الأمان:** `dbfilter` محدود بنطاق صحيح مع `list_db=False`، منع الوصول العام إلى Database Manager، TLS، Secret Manager، حساب PostgreSQL محدود الصلاحية، ACL وRecord Rules، اختبارات IDOR وCSRF، تقييد معدلات الطلبات، تعقب عمليات الإدارة، ترقية الإضافات المنضبطة. لا يَسمح النظام للتاجر برفع Python add-ons أو تنفيذ كود على الخادم.

## 4. الوحدات القياسية verified upstream مقابل وحدات NASQO

تمت مراجعة ملفات `__manifest__.py` للوحدات التالية في مستودع `odoo/odoo` عند الالتزام المثبّت `9cd6f090a8a21d9531c70ceec7f5c51271e24168` من سلسلة 19.0. عبارة **«أساس قياسي»** تعني توفر Module/Model ولا تعني مطابقة وظائف المرجع جميعها.

| المجال | وحدات Community القياسية | النماذج/الوظائف المستهدفة | الإضافة المخصصة عند الحاجة |
|---|---|---|---|
| المتجر الإلكتروني | `website_sale`, `sale_management`, `delivery`, `payment` | `website`, `product.template`, `sale.order`، Checkout وشحن | `nasqo_storefront` لتبسيط UX وRTL والباقات |
| جهات الاتصال | `base`, `mail`, `portal` | `res.partner`، أصحاب حسابات وزوار | `nasqo_partner_credit` لسقف المديونية والسياسات |
| الفوترة والقيود | `account`, `account_payment` | `account.move`, `account.move.line`, `account.payment`, `account.journal` | `nasqo_finance` لسندات/كشف/مصادقة مع Gap Review |
| الشراء | `purchase`, `purchase_stock` | `purchase.order`، موردون واستلام مشتريات | `nasqo_purchase_ui` لواجهة مبسطة فقط |
| المخزون | `stock`, `stock_account` | `stock.warehouse`, `stock.location`, `stock.picking`, `stock.move` | `nasqo_stock_reports` لتقارير RTL مخصصة |
| العملات | `base`, `account` | `res.currency`, `res.currency.rate`, قيود محاسبية | `nasqo_fx` لمصارفة نقدية/حسابات العملاء والتقريب |
| التقارير | تقارير النماذج القياسية، QWeb | فواتير وتقارير وأرشيف المستندات | `nasqo_reports` لمصادقة رصيد/كشف PDF/XLSX |
| الرسائل | `mail` وقوالب البريد الأساسية | قوالب وسجل اتصال داخلي | `nasqo_notifications` لمزوّد SMS/WhatsApp رسمي |
| الاشتراكات | طبقة SaaS **خارج Odoo** | Tenant plan / billing events / entitlements | `nasqo_control_plane` + `nasqo_billing` |
| النسخ الاحتياطي | PostgreSQL + Filestore + تخزين منفصل | Snapshot/Restore/Retention | `nasqo_backup_orchestrator` خارج Odoo |

**قيد توثيقي:** لم يثبت من المرجع المرئي كيفية عمل قيود «قيد تسوية» أو «رقم المستند» أو قيمة الشارات الحمراء؛ ستظهر كمتطلبات اكتشاف، لا كوظائف مؤكدة. كذلك لا توجد أدلة على آلية تفعيل التطبيق المرجعي داخليًا أو سياسات API الخاصة به.

## 6. قواعد البيانات والاتفاقيات المحاسبية

### 6.1 خرائط النماذج

| مفهوم الوثيقة | نموذج Odoo الأساسي | التعامل في NASQO |
|---|---|---|
| `accounts`, `account_groups` | `res.partner` للجهات، و`account.account`/`account.group` لدليل الحسابات | **لا** نخلط جهة اتصال مع حساب دفتر الأستاذ؛ تسلسل الحسابات في الواجهة يحتاج UX واضحًا |
| `account_balances`, `account_transactions` | بيانات مشتقة من `account.move.line` | View/Report مشتق، وليس جدول أرصدة قابلًا للتحرير |
| `journal_entries`, `journal_lines` | `account.move`, `account.move.line` | إضافة `external_operation_id` عند الحاجة مع Unique Constraint |
| `vouchers`, `transfers` | `account.payment`/`account.move` | Wizard وحقول إضافية حسب الحالات، لا ازدواج للحركة |

| `invoices`, `invoice_lines` | `account.move` (invoice/bill), `account.move.line` | لا تُكرر الفاتورة في جدول موازٍ |
| `warehouses`, `items`, `stock_movements` | `stock.warehouse`, `product.template`, `stock.move` | اتبع Odoo stock workflow والـUoM |
| `stock_transfers` | `stock.picking`, `stock.move` | تحقق من المصدر والوجهة وTracking |
| `quotations`, `orders` | `sale.order`, `purchase.order` | فصل اتجاه البيع عن الشراء |
| `attachments`, `message_logs` | `ir.attachment` و`mail.message` حيثما يناسب | إضافة سجل تكامل منفصل دون تسجيل محتوى سري |
| `licenses`, `license_events` | Control Plane DB | لا تربط أحقية باقة التاجر بترخيص جهاز Android |
| `backup_history`, `audit_logs` | Control Plane + central logs | سجل غير قابل للتعديل عمليًا، بعزل نطاق كل مستأجر |

### 6.2 ثوابت محاسبية إلزامية

- لكل قيد مرحّل `Σ debit = Σ credit` **بعملة الشركة**؛ فروقات الصرف تسجل في حسابات محددة بالسياسة.
- الرصيد الافتتاحي ينشئ قيدًا مقابلاً وفق حساب افتتاحي مفوض ومراجعة مسؤول مالي؛ لا يمكن إنشاء رصيد مباشرة في `res.partner`.
- `idempotency_key` أو `external_operation_id` يمنع تكرار سند/صرف/فاتورة عند النقر المزدوج أو إعادة محاولة API.
- تسجيل المستخدم والتاريخ ونوع العملية، ومنع حذف القيود المرحّلة بالطريقة المعتادة؛ التصحيح بآلية Cancel/Reversal الموثقة.
- اعتماد تواريخ العمل والمنطقة الزمنية والعملة وPrecision؛ تجنب Float في حاسبة صرف العملات.
- عرض «عليه/له» واصطلاح الإشارة حسب سياسة محاسبية موثقة ومتسقة لكل تقرير؛ لا تستنتجها من الأحمر/الأخضر في الصورة.
- التكاليف والأرباح في حركة المخزون تحدد بناءً على valuation method ومستندات فعلية؛ لا تساوي قيمة المخزون تلقائيًا إجمالي الأرباح.
- اختبارات بيئة مالية منفصلة ببيانات مُصطنعة قبل أي بيانات حقيقية.

| M2 – إثبات العزل بمتجرين | Tenant Registry، Provisioner، DB/Filestore لكل متجر، HTTP routing | إنشاء متجرين بعملية متكررة آمنة؛ 0 وصول متقاطع | P0 |
| M3 – متجر MVP | كتالوج وسلة وCheckout وطلبات، COD/تحويل وتوصيل واختبارات عربية | طلب كامل end-to-end + RTL على الجوال + الاستعادة | P0 |
| M4 – محرك مالي مُعتمد | تحليل gap في `account` ثم Opening / Journals / Vouchers / Statements / FX | جميع اختبارات القيد والرصيد والعملة والعكس والتزامن PASS | P0-F |
| M5 – مخازن ومشتريات وتقارير | الموردون، المخازن، التحويل، مردودات، تقارير كشف وPDF/XLSX | عدم تكرار stock moves ومطابقة أرصدة وتقارير | P1 |
| M6 – SaaS تجاري آمن | باقات + Trial + Entitlements + تجديد + فواتير منصة + Support | لا فقد بيانات عند انتهاء الخطة، ولا تعطيل Checkout بغير إنذار | P0 مدفوع |
| M7 – تكاملات اختيارية | WhatsApp/SMS، Google Drive export اختياري، دعم متعدد القنوات | موافقة صريحة + Secret handling + اختبارات فشل ومعدل إرسال | P2 |
| M8 – إطلاق تدريجي | Pilot لعملاء اختبار، استعادة فعلية، مراقبة، Incident Runbooks، SLA | موافقة أمنية ومحاسبية، Rollback مثبت، ميزانية ومراقبة | إطلاق |

**تداخل المسارات:** تبدأ M4 في فرع مالي منفصل بعد M1؛ لا تشترط M3 إتمام M4. النسخ الاحتياطي والعزل مطلوبان في M2–M3 وقبل نشر أي بيانات. تقاس كل مرحلة بـPR مستقل صغير، CI، Test Report ومراجعة Security/Finance عند اللزوم.

## 9. المتطلبات غير الوظيفية والأمان والنسخ الاحتياطي

| محور | الحد الأدنى المقترح لإثبات الاستعداد |
|---|---|
| الهوية | MFA للإدارة، RBAC، sessions آمنة، تغيير كلمات السر، لا أسرار ضمن Git/Logs |
| العزل | اختبارات API/DB/Filestore/Domain على متجرين على الأقل قبل كل إصدار ذا صلة |
| التشغيل | قنوات فصل Dev/Staging/Production، ضبط إصدارات وDigests معتمدة، صور دون أسرار |
| قواعد البيانات | مستخدم مخصص ذو أقل صلاحية، نسخ متسقة، فحص ترحيل Schema لكل Tenant |
| النسخ | نسخة DB+Filestore معًا، تشفير أثناء النقل والتخزين، تخزين منفصل، دورية اختبار الاستعادة |
| المرونة | Queue idempotent، Backoff+Dead-letter، عدم ترك نطاق عام على بيئة فاشلة |
| المراقبة | إنشاء متجر، زمن استجابة، صحة Checkout، فشل Backup، سعة قرص، فشل الدفع اليدوي، أخطاء مالية |
| الخصوصية | أقل قدر من بيانات العملاء، غرض واضح للمراسلة، حدود احتفاظ، حق استخراج البيانات |
| الجودة | Unit / Odoo integration / HTTP E2E / RTL visual / Restore / Security / Accessibility |

**أهداف أولية غير معتمدة كـSLA:** 99.5% توافر عند Pilot، RPO ≤ 24h، RTO ≤ 8h بعد إثبات اختبارات النسخ والاستعادة، وProvisioning غالبًا ≤ 10 دقائق. تُراجع الأهداف بناءً على قياسات وميزانية قبل إعلانها تجاريًا.

**سياسة انتهاء الاشتراك:** فصل استحقاق الخدمة عن ملكية البيانات. قبل الإيقاف: إشعار، فترة سماح، وضع قراءة/تصدير إن كان مناسبًا، عدم حذف البيانات تلقائيًا دون سياسة متفق عليها، وتتبع كل إجراء.

9. متطلبات التقارير المالية وامتثال الفواتير والضرائب في اليمن؛ تحتاج موافقة محاسب/مستشار محلي.
