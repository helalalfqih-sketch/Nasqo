# خطة الدفعات التالية — تصميم NASQO الأصلي

هذه خطة تنفيذ، وليست وظائف مكتملة أو موافقة على بدء M3. المرجع الملزم هو
`IMPLEMENTATION_PLAN_v1.0.md` وحالات AT-001–AT-032، مع المتطلبات الوظيفية في
وثيقة المحاسب الذكي برو الموسعة ذات 11 صفحة. لا تُنسخ شيفرة أو صور أو هوية
المرجع. يُراجَع آخر تقرير CI و`AI_HANDOFF.md` قبل كل دفعة.

## خط الأساس الذي تبني عليه الخطة

- معاملات كل متجر في قاعدة Odoo وFilestore مستقلين؛ سجل التشغيل خارجها.
- تجربة المشغل المحلي تثبت عقد التهيئة والعزل والاستعادة؛ ليست تسجيلًا ذاتيًا
  أو Control Plane تجاريًا. لا يُنقل SQLite التجريبي إلى الإنتاج كما هو.
- المصدر المثبت يحوي `account` و`account_payment` و`purchase` و`stock` وتراخيصها
  LGPL-3. وجود الوحدة لا يثبت توفر تقارير Enterprise أو اكتمال التوطين.
- توجد وظائف أصلية للافتتاحي (`company.py`)، وتوازن وعكس القيود
  (`account_move.py`)، وحقل حد ائتماني (`partner.py`). تُختبر قبل تقرير أي إضافة.
- YER موجودة في المصدر؛ إعداد اللغة والعملة والتقريب والضرائب ما زال قرارًا
  واختبارًا مستقلًا. لا تُستنتج سياسة مالية من لون أو ترتيب شاشة مرجعية.

## بوابة الخروج من التجربة قبل M3

1. اعتماد دليل M1/M2 الكامل على نفس الشيفرة، وفحص صور التشغيل الفعلية بلا
   استثناءات خفية. إعادة تشغيل مصادقة المتجرين والنسخ بعد أي تغيير في الصور.
2. مراجعة image digests وفحص تاريخ Git وأقل الصلاحيات؛ توجد أدلة CI ناجحة
   للنسخة التجريبية `f1ae638`، ويظل اعتماد التشغيل التجاري قرارًا مستقلًا.
3. اعتماد فصل إنشاء المتجر بواسطة مشغل موثوق عن التسجيل التجاري؛ استكمال
   AT-001 وAT-006 وAT-030 قبل فتح التهيئة للعامة، مع audit ومحاكاة انقطاع HTTP/DB.
4. تحديد مالك قرار المحاسبة والدفع والاحتفاظ بالمعلومات. لا توجد موافقة إطلاق
   أو ترحيل أو دمج ضمن هذه الجولة.

يجب أن يبقى A/B معزولَين أثناء إنشاء الطلبات وتسجيل المستخدمين.

## M4 — المالية، دفعات صغيرة بعد اعتماد الفجوات

أول PR مالي يضيف اختبارات قدرة Community ومصفوفة gap فقط. لكل متطلب تُسجل
شاشة/نموذج/صلاحية قياسية، تجربة تشغيل، ما ينقص، وقرار إعادة الاستخدام أو التوسيع.
لا تُنشأ وحدات `nasqo_finance` أو `nasqo_fx` أو غيرها اعتمادًا على الاسم وحده.

| الدفعة | النماذج ومكان التوسيع المحتمل | اختبارات وبوابة قبول |
|---|---|---|
| M4.0 قدرة Community | `account`/`account_payment`؛ وثيقة gap مع fixtures | AT-032: دفتر/كشف/تقارير/تسوية/صلاحيات متاحة فعليًا؛ لا إعلان عن Enterprise |
| M4.1 حسابات وافتتاحيات | `res.partner`, `account.account`, `account.move`؛ wizard داخل `nasqo_finance` عند الحاجة | AT-011/012: حساب بلا افتتاحي = صفر حركة؛ رصيد افتتاحي مع طرف مقابل معتمد، اتجاه صحيح وقيد متوازن واعتماد مخوّل |
| M4.2 سند قبض/صرف وتحويل | `account.payment`, `account.journal`, `account.move`؛ بيانات المرجع والمرفق والعملية فقط | AT-014/015: صندوق/تاريخ/عملة/مبلغ صحيحة، نقرتان وطلبان متزامنان يولدان قيدًا واحدًا، rollback كامل عند الفشل |
| M4.3 تصحيح وترابط مستندات | قيود وفواتير Odoo القياسية وreversal | AT-013/031: نقد/آجل ومردود مترابطة؛ رفض تعديل/حذف الأثر المرحّل عبر UI وRPC؛ تصحيح بعكس مع سجل السبب والمخوّل |
| M4.4 كشوف ومصادقات | `account.move.line` ومجموعات ORM؛ `nasqo_reports` فقط للفجوات | AT-016/017: رصيد ما قبل الفترة، متتابع وإجماليات، استقرار الأرقام مع الفرز، مصادقة PDF بلا وصول غير مخوّل |
| M4.5 صرف العملات | `res.currency`, `res.currency.rate`, `account.move`؛ مستند عملية `nasqo_fx` مرتبط بالقيد لا دفتر موازٍ | AT-018/019: شراء/بيع وسعر مؤرخ واتجاه معلن، rounding وFX difference، العودة من إنشاء حساب دون فقد المسودة أو ترحيلها |
| M4.6 ضوابط الائتمان | `res.partner` وحدود Odoo؛ `nasqo_partner_credit` عند الحاجة | AT-020: تحذير أو منع وفق السياسة؛ طلبان متزامنان لا يتجاوزان السقف دون تفويض موثق |

ضوابط مشتركة:

- رصيد العميل ليس حقلًا مستقلًا قابلًا للتحرير؛ مصدره البنود المحاسبية وفق
  الحسابات والعملات والسياسات المعتمدة. لا جدول موازٍ للفواتير أو القيود.
- معرف العملية مع fingerprint وقيد uniqueness داخل PostgreSQL يمنع تكرار الأثر؛
  المفتاح نفسه مع بيانات مختلفة يُرفض. يتحقق الاختبار من الحالة بعد commit.
- تُستخدم آلية توازن Odoo وتقريب العملة، مع Decimal عند تحليل مبالغ وأسعار
  الاستيراد/حدود التكامل، دون تغيير أنواع حقول Odoo Core أو تعطيل التحقق.
- تُحفظ عملة الأساس وعملة العملية وتاريخ وسعر واتجاه التحويل ومصدره؛ يُختبر
  السعر المباشر والعكسي والتقريب والفرق. لا استخدام لسعر «اليوم» في حركة مؤرخة.
- الصلاحيات تشمل إنشاء المسودة واعتمادها وعكسها والمرفقات؛ الواجهات وحدها
  ليست حاجزًا. لا `sudo` عام لتجاوز أخطاء الصلاحيات.

قرارات مالية لازمة: تعريف له/عليه في كشف العميل وكشف المورد، دليل الحسابات
والافتتاحي المقابل، صلاحيات الاعتماد والعكس والفترات، الضريبة، العملة الأساسية،
مصدر سعر الصرف وتاريخه، سياسة السقف. تعتمدها جهة محاسبية مختصة قبل البناء المالي.

لا يُحدَّث المخزون مباشرة في SQL ولا يُنشأ جدول كميات ثانٍ. fixtures تشمل
مخزنين وموقعًا داخليًا وموردًا ومرتجعًا وصنفًا بوحدتين. تختبر إعادة الإرسال
وrollback وتعطيل الصلاحية؛ لا تُفترض سياسة negative stock أو valuation method.

## M6 — الباقات واستحقاق الخدمة وفوترة المنصة

Control Plane خارج قواعد معاملات التجار. يُحفظ فيه التاجر وملكية المتجر
والاشتراك وإصدار الباقة وentitlement وسجل audit وjob/outbox؛ لا ينسخ أرصدة
عملاء المتجر أو قيوده. تقنية API/queue وموفر الهوية اختيار معماري منفصل.

| الدفعة | العقد المطلوب | القبول |
|---|---|---|
| M6.1 هوية وملكية | تسجيل وتحقق، owner/store binding، MFA للدعم، تفويض مؤقت مسجل | AT-001/006: غير المتحقق لا ينشئ متجرًا؛ الدعم غير المخوّل لا يقرأ البيانات وتُسجَّل المحاولة |
| M6.2 تهيئة موزعة | حالات provisioning وفواصل retries وdead-letter وdomain ownership | AT-003/030 كاملان: قتل worker، انقطاع DB/HTTP، استئناف بلا إنشاء موارد أو متجر مكشوف مكرر |
| M6.3 إصدار الباقة | trial/active/grace/restricted/cancelled واستحقاقات ذات إصدار | AT-027: انتهاء أو إلغاء لا يحذف بيانات؛ سياسة قراءة/تصدير معتمدة وتجربة استعادة |
| M6.4 فوترة المنصة | فاتورة الاشتراك تخص NASQO والتاجر، خارج دفتر متجره | webhook موثّق، duplicate/out-of-order آمن، عدم تفعيل خطة قبل تحقق السداد، reconciliation يومي اختباري |

قرارات قبل التنفيذ: السعر والعملة والحدود وفترة السماح وآلية الاعتراض/التصدير
والاحتفاظ. لا تُحفظ كلمات مرور خام ولا بيانات بطاقات، ولا يُؤدي تعليق الاشتراك
إلى حذف DB أو Filestore أو مفاتيح النسخ.

## M7 وM8

M7 مستقل: مزوّد رسمي SMS/WhatsApp، موافقة موثقة لكل غرض، قوالب، outbox وعملية
واحدة عند retry، سياسة تلقائي/بعد التأكيد/لا ترسل. AT-025 يثبت صفر outbound
فعلًا؛ AT-026 يختبر التأكيد والإلغاء وإعادة المحاولة المحدودة. لا إرسال حقيقي
في CI، ولا حفظ token داخل المتجر أو Logs.

M8 شرط إطلاق: threat model ومراجعة صلاحيات، TLS/DNS، quotas، تحديثات الصور،
فحص الأسرار والتبعيات، monitoring، نسخ خارج المضيف وتدوير مفاتيح، استعادة
مستقلة مقاسة وrollback. تُقاس RPO/RTO قبل إعلان SLA. تحفظ نسخة PostgreSQL
وFilestore وهوية المستأجر وإصدار Odoo والإضافات معًا، ويرفض عدم تطابقها.

## قاعدة التسليم لكل دفعة

PR صغير بلا دمج تلقائي، تغييرات ORM/inheritance فقط، بيانات اصطناعية، أدلة
Unit/Odoo/HTTP/RTL/ACL الملائمة، PASS/FAIL/BLOCKED لكل AT، تحديث README وHandoff،
وقرارات المرحلة التالية. نجاح الاختبارات لا يجيز نشرًا أو ترحيلًا إنتاجيًا.
