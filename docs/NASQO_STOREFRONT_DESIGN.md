## 2. البنية الفعالة ومصادر الإثبات

| المصدر داخل الأرشيف | ما ظهر فعليًا | القرار |
| --- | --- | --- |
| `templates/index.json` | خمسة أقسام فعالة: carousel، promos، categories، products، services | الاستفادة من ترتيب رحلة الشراء وإعادة تصميمه؛ عدم نقل الأقسام حرفيًا |
| `sections/indexes-home-carousel.liquid` | هو نوع القسم الرئيسي المستخدم في القالب الحالي | عدم اعتبار ملف `indexes-mobile-home.liquid` الأقدم نقطة البداية الفعالة |
| `templates/product.json`، `collection.json`، `cart.json` | أقسام منتج وتوصيات وتصنيف وسلة مخصصة | رسم حالات المنتج والتصنيف والسلة في نسقو |
| `layout/theme.liquid` | RTL بحسب اللغة، shell وتذييل مخصصان، و14 مرجع CSS مخصصًا دون شرط، إضافة إلى أصول مشروطة | بناء طبقة CSS واحدة محصورة في المتجر؛ قياس الأداء لاحقًا بدل افتراض تحسنه |
| `snippets/indexes-global-shell.liquid` | بحث وسلة وحساب وتنقل جوال؛ اعتماد على بيانات Shopify customer | إعادة تصميم التنقل وربط الحساب لاحقًا ببوابة Odoo |
| `snippets/indexes-footer.liquid` | تسوق وسياسات ودعم وروابط إضافية مشروطة | تذييل قابل للطي في الجوال، وسياسات خاصة بكل تاجر |
| `snippets/indexes-manager-dashboard.liquid` وشرط التخطيط | الظهور محصور بـ`request.design_mode` وروابط إلى Shopify Admin | ليست لوحة إدارة SaaS ولا إثباتًا لفصل أدوار نسقو؛ لا تُنقل إلى متجر المشتري |
| `assets/indexes-quick-order.js` | طلب إضافة للسلة عبر Shopify Ajax | استبداله بمسارات `website_sale`، لا نقل JavaScript كما هو |
| `assets/indexes-order-bridge.js` | عقد عميل مع App Proxy محدود بالمسار `/apps/indexes-orders` وHTTPS ونفس الأصل، والتحقق من التهيئة، و`idempotencyKey` | توجد ضوابط في العميل، لكن الخادم غير موجود في الأرشيف؛ لا يمكن إثبات صحة الطلب أو الدفع منه |

توجد طبقات CSS كثيرة واستخدامات `!important` تستحق المراجعة؛ هذه ملاحظة
صيانة وليست نتيجة قياس أداء. توجد صور تعتمد على Shopify CDN وروابط أعمال
خارجية؛ لم تُنسخ تلك الصور أو بيانات الاتصال إلى التصميم الجديد. واجهة تثبيت
التطبيق لا تكفي وحدها لإثبات دعم عمليات الشراء Offline.

لم يُعثر على ملف باسم LICENSE أو LICENCE أو COPYING داخل الأرشيف. لا يثبت
ذلك غياب ترخيص أو حق إعادة الاستخدام؛ يلزم فحص الترخيص قبل أي إعادة توزيع
للشيفرة أو الأصول الأصلية. المعاينة الحالية لا تعيد توزيعها أصلًا.

## 3. التصميم المنفذ

الهوية: أخضر داكن `#153C42`، لون إجراء `#096B63`، ذهبي هادئ `#DEB66D`،
وخلفية `#F4F8F7`. هذا استمرار لاتجاه `addons/nasqo_storefront` الحالي، مع
تخطيط جديد يختلف عن هوية Indexes الحمراء وعن التطبيق المحاسبي المرجعي.

- رأس صفحة ببحث ظاهر وسلة ومفضلة وحساب.
- منتج رئيسي واحد ورسم أصلي، ثم أربعة أقسام وشبكة منتجات.
- ثمانية منتجات اصطناعية، بأسعار YER توضيحية لا تُغيّر إعدادات عملة ERP.
- تصفية وبحث وترتيب ومفضلة، ونوافذ تفاصيل مع اللون والكمية.
- سلة تُعدّل الكمية وتمنع تجاوز المخزون التجريبي المجمّع عبر الألوان.
- مراجعة طلب بخياري توصيل تجريبي 1,500 أو استلام مجاني، وخياري دفع للعرض فقط.
- بوابة مشتري توضيحية بطلب اصطناعي معلّم بوضوح، وتذييل ومركز مساعدة.
- RTL، خطوط Noto محلية مع OFL، وتركيز لوحة مفاتيح وEscape وتنقل جوال.

الرسومات الثمانية والعلامة الهندسية أُنشئت لهذه المعاينة. لا تُعرض شعارات Odoo
أو المحاسب الذكي أو صور منتجات المرجع. لا يوجد API أو backend أو تسجيل دخول
حقيقي. `localStorage` يحفظ معرفات المنتجات والألوان والكميات والمفضلة فقط؛
ولا يُطلب اسم أو هاتف أو عنوان أو بطاقة. الأسعار والقيود في JavaScript توضح
التفاعل، ولا تصلح مصدر حقيقة ماليًا أو ضابط أمان عند الدمج الفعلي.

## 6. مراحل التنفيذ التالية بعد الاعتماد

1. **بوابة الأساس:** مراجعة PRs المعلقة وتوحيد مصدر/runtime، ثم إغلاق موانع
   عزل M1/M2 وRBAC حسب الخطة. التصميم لا يستبدل هذه البوابة.
2. **هيكل M3:** إدخال قوالب الرأس والتذييل والأقسام وCSS في
   `addons/nasqo_storefront` في قاعدة اصطناعية منفصلة، مع إعدادات لكل موقع.
3. **المنتجات والسلة:** ربط ORM ومسارات Odoo؛ اختبارات السعر وقائمة الأسعار
   والنشر والمتغيرات والمخزون وتغيير الكمية والسلة الفارغة، بين متجرين.
4. **إتمام الطلب والبوابة:** اختيار مزود الدفع والتوصيل وفق نطاق الخطة؛ إثبات
   صلاحيات Portal، منع تكرار الطلب، وعدم تأكيد دفع فاشل. COD/التحويل البنكي
   لا يُفعّلان بمجرد وجودهما في المعاينة.
5. **القبول:** جولات متصفح وجوال حقيقي، لوحة مفاتيح، قارئ شاشة، العربية،
   reconnect وفشل HTTP/DB، اختبارات العزل والمرفقات، وخطة رجوع مثبتة قبل النشر.
6. **المراحل اللاحقة:** المحاسبة والمخازن والتقارير والاشتراكات تبقى حسب M4+
   والخطة المعتمدة؛ لا إنشاء جداول موازية للفواتير أو الحركات المالية، ولا
   دمج اشتراكات المنصة في دفاتر متاجر العملاء.

قرارات المنتج الباقية: اعتماد اتجاه التصميم، محتوى وصور المنتجات المرخصة،
سياسات كل تاجر، البلد والعملة والضرائب ومزودو الدفع والتوصيل. لا يلزم اتخاذها
لتجربة المعاينة الحالية، لكنها مطلوبة قبل قبول متجر متصل.
